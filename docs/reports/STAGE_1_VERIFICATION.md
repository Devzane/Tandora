## 1. Executive Summary

Stage 1 implementation establishes the complete core domain data model, Alembic schema migrations, Pydantic contracts, service layer logic, REST API endpoints, and a minimal server-rendered local web UI for the Tandora lead management and outreach application.

All 21 domain tables documented in `docs/DATABASE_SCHEMA.md` have been implemented as declarative SQLAlchemy 2.x models and verified through an automated Alembic revision (`4a386b6fd0d9_create_initial_21_tables.py`). Deterministic prospect deduplication (primary LinkedIn canonicalization, secondary normalized email, tertiary name+company candidate duplicate review flagging) and independent channel provenance tracking for emails and phone numbers have been fully implemented and verified with unit tests. Multi-level suppression cascading (company, person, and address levels) automatically cancels active follow-up schedules and records append-only operational audit trails. A server-rendered local web UI powered by FastAPI and Jinja2 templates provides immediate management of organizations, opportunities, contacts, and suppressions without any JavaScript build toolchain or external cloud dependencies.

The automated test suite expanded from 12 tests (Stage 0) to 33 tests (Stage 1), achieving a 100% pass rate in 3.14 seconds with zero deprecation warnings and zero failures.

## 5. Technical Issues Identified & Resolved

1. **SQLAlchemy Metadata Column Conflict**:
   - *Issue*: In declarative models, defining a column named `metadata` on `AuditLog` collides with the model's `Base.metadata` MetaData instance, triggering `SAWarning` and shadowing table reflection.
   - *Fix*: Mapped the database column name `"metadata"` to the Python attribute `metadata_json` using `mapped_column("metadata", Text, nullable=True)`. This preserves exact database schema naming without Python attribute shadowing.
2. **Missing `python-multipart` Dependency**:
   - *Issue*: FastAPI requires `python-multipart` to parse form-encoded POST requests (`Form(...)`). TestClient raised `RuntimeError: Form data requires "python-multipart" to be installed`.
   - *Fix*: Added `"python-multipart>=0.0.9"` to `pyproject.toml` and installed it in `.venv`.
3. **In-Memory SQLite Multi-Connection Table Isolation**:
   - *Issue*: In-memory SQLite (`sqlite:///:memory:`) creates an isolated transient database per connection. During test execution with multiple client requests, secondary connections lacked table schemas, raising `no such table: companies`.
   - *Fix*: Configured `poolclass=StaticPool` in `backend/tests/conftest.py`, ensuring all connections in a test share the exact same in-memory database instance.
4. **Starlette `TemplateResponse` Keyword Signature**:
   - *Issue*: Newer Starlette versions define `TemplateResponse(self, request, name, context, ...)` rather than accepting `(name, context)` positionally. Passing `("dashboard.html", {...})` caused Starlette to pass the context dictionary as `name`, raising `TypeError: unhashable type: 'dict'`.
   - *Fix*: Updated all 11 UI endpoints in `backend/app/ui/routes.py` to use explicit keyword arguments: `templates.TemplateResponse(request=request, name="...", context={...})`.
5. **Contact `full_name` Not-Null Constraint**:
   - *Issue*: The schema specifies `contacts.full_name` as `NOT NULL`. Initial contact creation passed individual names without populating `full_name`.
   - *Fix*: Implemented automated computation: `full_name = f"{first_name} {last_name or ''}".strip()` on contact creation and updates.
