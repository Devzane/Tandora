# Project Specification — Tandora Lead Management & Outreach Application

## 1. Product Purpose

Tandora is an AI-powered lead management and personalized outreach application designed to help an individual professional find opportunities, organize contacts, and conduct high-quality email outreach campaigns at scale.

The application supports two primary workflows:

- **Employment outreach**: Finding relevant job opportunities, capturing company and job description data, identifying hiring decision-makers, and generating personalized professional emails.
- **Freelance client acquisition**: Identifying companies that may require cloud, DevOps, AI/ML, or automation services; capturing company and contact data; and generating personalized business development emails.

## 2. Target Users and Use Cases

One person, operating the application locally on a Windows 11 laptop. No multi-user, multi-tenant, or enterprise features are required at launch.

### Primary Use Cases

| ID | Use Case |

## 3. Functional Requirements

### 3.1 Data Capture

- FR-01: The system must support capturing multiple companies.
- FR-02: Each company must support multiple opportunities (jobs or freelance engagements).
- FR-03: Each company must support multiple contacts.
- FR-04: Each contact must support multiple roles (e.g., Recruiter, CTO, Founder).
- FR-05: Each contact must support multiple email addresses.
- FR-06: One email address per contact must be designated as the selected outreach address for each outreach thread.

### 3.2 Email Verification

- FR-07: The system must verify email addresses through the Reoon Email Verifier API.
- FR-08: Verification results must be stored and include: status (safe, catch-all, invalid, unknown), timestamp, and Reoon response payload.
- FR-09: `safe` addresses may proceed to draft generation automatically.
- FR-10: `catch-all` addresses must be flagged for manual review. The user must explicitly approve the use of a catch-all address before an email is generated or sent.
- FR-11: `invalid` and `unknown` addresses must not be used for outreach.
- FR-12: The system must track Reoon API credit consumption.

### 3.3 AI Draft Generation

- FR-13: The system must generate personalized email drafts using the Gemini API.
- FR-14: Ollama must be supported as an optional local LLM provider.
- FR-15: The LLM provider must be switchable via configuration, not code changes.
- FR-16: Generated drafts must be stored with versioning. Each generation creates a new draft version.
- FR-17: Draft generation must reference company, opportunity, and contact context.
- FR-18: Drafts must include subject line and body.

### 3.4 Approval Workflow

- FR-19: No email, including follow-ups, may be sent without explicit user approval.
- FR-20: Approvals must be recorded with timestamp and the approved draft version.
- FR-21: Editing a draft after generation creates a new version; the edited version requires re-approval.
- FR-22: Follow-up emails are independent approval events.

### 3.5 Outreach and Sending

- FR-23: Approved emails must be sent via Zoho SMTP.
- FR-24: The global daily sending limit is 20 messages (including follow-ups).
- FR-25: The system must maintain a global pause/resume toggle that completely halts outbound sending.
- FR-26: When paused, no emails are sent, even if approved and scheduled.
- FR-27: One recipient address must be used per outreach thread. The system must not send differently-worded duplicates to multiple addresses belonging to the same person.
- FR-28: Outreach history must be recorded per contact per opportunity.

### 3.6 Follow-ups

- FR-29: Follow-up messages must be scheduled at day 3, day 7, and day 14 after the initial email.
- FR-30: Each follow-up must be independently generated by the LLM and independently approved.
- FR-31: If a reply is received before a follow-up is due, the follow-up must be automatically suppressed.
- FR-32: Suppressed follow-ups must be logged.

### 3.7 Reply and Bounce Tracking

- FR-33: The system must monitor the Zoho IMAP inbox for replies.
- FR-34: Replies must be associated with the originating outreach thread.
- FR-35: Bounced messages must be detected and recorded.
- FR-36: Contacts with bounced addresses must be flagged in the system.

### 3.8 Google Sheets Synchronization

- FR-37: The system must support manual bidirectional synchronization with Google Sheets.
- FR-38: Synchronization is triggered by the user, not automatically.
- FR-39: Conflicts (data changed in both Sheets and the local database) must be detected and surfaced to the user for resolution.
- FR-40: Synchronization must be idempotent. Running it twice must not create duplicate records.

### 3.9 Scheduler

- FR-41: A lightweight persistent scheduler must run locally to process follow-up sending at the correct time.
- FR-42: The scheduler must respect the global pause toggle and the daily sending limit.

### 3.10 Audit Logging

- FR-43: Every significant system event must be written to an audit log: draft generation, approval, sending, reply receipt, bounce detection, follow-up suppression, synchronization.
- FR-44: Audit log entries must be immutable.

---

## 5. Constraints

- **Database**: SQLite only. No hosted database services.
- **LLM**: Gemini API (primary), Ollama (optional local fallback). No other LLM providers required at launch.
- **Email provider**: Zoho (SMTP outbound, IMAP inbound).
- **Email verification**: Reoon only.
- **Spreadsheet sync**: Google Sheets only.
- **Sending limit**: 20 emails per day, globally (not per campaign).
- **Approval**: Mandatory. No automatic sending of unapproved emails, ever.
- **Catch-all addresses**: Require explicit manual approval before use.
- **Deduplication**: One selected address per person per outreach thread.
- **Platform**: Windows 11 local deployment only at launch.

---

## 6. Initial Scope

The initial implementation covers:

1. Backend API (FastAPI + SQLite + SQLAlchemy + Alembic).
2. Chrome Extension for capturing company/opportunity data from browser pages.
3. AI draft generation via Gemini API.
4. Manual approval workflow.
5. Zoho SMTP sending with daily quota enforcement.
6. Zoho IMAP reply and bounce monitoring.
7. Reoon email verification.
8. Follow-up scheduling.
9. Google Sheets bidirectional sync (manual trigger).
10. Audit logging.
11. Lightweight local scheduler (APScheduler or equivalent).

---

## 7. Deferred Features

The following are explicitly out of scope for the initial implementation. They must not be designed into the initial architecture in ways that complicate the core system.

| Feature | Reason Deferred |
|---------|----------------|
| User registration and authentication | Single-user application |
| Multi-user permissions and roles | Not required at launch |
| Billing and subscription management | Commercial feature |
| Payment processing | Commercial feature |
| Enterprise administration panel | Commercial feature |
| Multi-tenant infrastructure | Commercial feature |
| AWS or cloud migration | Local deployment for now |
| Public-facing web UI | Backend + extension sufficient for now |

The codebase must be structured so these can be added later without a full rewrite.

## 8. Acceptance Criteria

### AC-01: Data Model
- Companies, opportunities, contacts, roles, and email addresses can all be created and retrieved via the API.
- Multiple items at each level are supported.

### AC-02: Email Verification
- Reoon verification runs and stores results.
- Safe addresses pass automatically.
- Catch-all addresses are flagged and cannot be used without explicit approval.
- Invalid addresses are blocked from outreach.

### AC-03: AI Drafting
- Drafts are generated using context from the company, opportunity, and contact.
- Drafts are stored with version numbers.
- Switching LLM provider requires only a config change.

### AC-04: Approval Gate
- No email can be sent without an approval record in the database.
- Each follow-up requires its own approval.

### AC-05: Sending
- Emails are sent via Zoho SMTP.
- The daily limit of 20 is enforced.
- The global pause prevents all sending.
- One address is used per outreach thread.

### AC-06: Follow-ups
- Follow-ups are scheduled for days 3, 7, and 14.
- Each is independently approved.
- A reply suppresses pending follow-ups.

### AC-07: Tracking
- Replies are detected and linked to the originating thread.
- Bounces are detected and contacts are flagged.

### AC-08: Google Sheets Sync
- Manual sync imports and exports data correctly.
- Conflicts are surfaced, not silently overwritten.
- Running sync twice does not create duplicates.

### AC-09: Audit Log
- Every significant event is logged.
- Log entries cannot be deleted or modified via the application.

### AC-10: Chrome Extension
- The extension can capture the current page URL, title, and selected text.
- Captured data is submitted to the backend API.
